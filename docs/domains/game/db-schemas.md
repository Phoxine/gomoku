# Game Database Schema

The `games` table stores each game. Its model and initial migration are in `app.domain.game`.

| Column | PostgreSQL type | Nullable | Django default or automatic value | Database default | Constraints | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `id` | UUID | No | Generated UUID4 | None | Primary key | Game identifier. |
| `board` | JSONB | No | Fresh 15×15 empty board | None | 15 rows of 15 integer cells with values `0`, `1`, or `2`. | Board cells, initially all zero. |
| `current_player` | SMALLINT | No | `1` | None | Must be `1` or `2`. | Player whose turn it is, or the last mover when the game has ended. |
| `status` | VARCHAR(16) | No | `in_progress` | None | Must be `in_progress`, `won`, or `draw`. | Game status. |
| `winner` | SMALLINT | Yes | `null` | None | Must be `1` or `2` for a won game and null otherwise. | Winning player, if any. |
| `mode` | VARCHAR(16) | No | `two_player` | `two_player` | `game_mode_valid` permits only `two_player` and `cpu`. | Turn ownership, chosen at creation and immutable through game commands. |
| `history_start_revision` | SMALLINT | No | `0` | None | `game_history_start_revision_valid` permits `0` through `225`. | Fixed revision at which move recording began for this game. |
| `created_at` | TIMESTAMP WITH TIME ZONE | No | Set on creation | None | None | Creation time. |
| `updated_at` | TIMESTAMP WITH TIME ZONE | No | Set on save | None | None | Last update time. |

The [mode migration](../../../src/app/domain/game/migrations/0002_game_mode.py) supplies `two_player` for existing rows and inserts from older app versions that omit `mode`. Existing game data and timestamps are preserved. The game revision is derived from the occupied cells of the saved board.

The migration adds the column and validates the mode constraint in one transaction. Constraint validation scans the table, and the schema change can block concurrent writers until it commits. In a rollout with overlapping app versions, apply the migration first and set `CPU_CREATION_ENABLED=false` on every new writer until the older writers are out of service. The setting defaults to enabled. Older writers can still create and update two-player games, but they cannot enforce CPU turn ownership.

| Index | Columns | Type | Purpose |
| --- | --- | --- | --- |
| `games_pkey` (B-tree) | `id` | Primary key | Identifies a game. |

Check constraints enforce the player, status, winner, and status/winner consistency rules. Django's positive small integer fields also produce the PostgreSQL checks `games_current_player_check` and `games_winner_check` for nonnegative values. The table has no foreign keys.

The PostgreSQL board constraint applies to all database writes and rejects decimal cells such as `1.0`, consistent with the game service's integer-cell validation.

## Move history

The `game_moves` table stores one row per accepted stone. Move numbers are one-based and equal the number of occupied cells after the move. Coordinates use `board[y][x]`.

| Column | PostgreSQL type | Nullable | Django default or automatic value | Database default | Constraints | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `id` | BIGINT | No | Generated by PostgreSQL | Identity | Primary key | Move row identifier. |
| `game_id` | UUID | No | None | None | Foreign key to `games.id` | Game that owns the move. |
| `move_number` | SMALLINT | No | None | None | `game_move_number_valid` permits `1` through `225`. | Board revision after the move. |
| `player` | SMALLINT | No | None | None | `game_move_player_valid` permits `1` (black) and `2` (white). | Player who placed the stone. |
| `x` | SMALLINT | No | None | None | `game_move_x_valid` permits `0` through `14`. | Column of the stone. |
| `y` | SMALLINT | No | None | None | `game_move_y_valid` permits `0` through `14`. | Row of the stone. |

| Index | Columns | Type | Purpose |
| --- | --- | --- | --- |
| `game_moves_pkey` (B-tree) | `id` | Primary key | Identifies a move row. |
| `game_move_number_unique` (B-tree) | `game_id`, `move_number` | Unique | Enforces numbering per game and supports ordered history reads. |
| `game_move_position_unique` (B-tree) | `game_id`, `x`, `y` | Unique | Records each position at most once per game. |

The composite indexes cover lookups by `game_id`. Django cascades deletion of a game to its moves. The PostgreSQL foreign key uses `NO ACTION`, so a direct SQL delete must remove dependent rows within the same transaction.

Pause and drain all game writers before applying the [move history migration](../../../src/app/domain/game/migrations/0003_game_move_history.py). It backfills `history_start_revision` from the occupied-cell count of each existing board, preserving the saved game state and timestamps. The migration inserts no move rows. A game with 12 stones starts recording at move 13. New empty games start at revision zero. The repository uses the supplied board's occupied-cell count on creation, and fixtures that insert nonempty boards directly specify their starting revision explicitly.

The migration writes existing rows and takes schema locks. After activation, an older writer's insert would omit the required boundary and fail. Its board update could still succeed and leave a gap in the recorded moves. Keep writers paused through verification and resume with history-aware writers only. If the application rolls back to a version without history support after recording begins, keep game writes paused and retain the stored history and boundary.
